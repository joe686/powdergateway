## 四、范围膨胀风险

### 4.1 v0.5.0 战略功能 4-6 周

- FN-BIZ 业务菜单生成 + SYS-3 升级 双大改造
- 用户 2026-07-26 拍板"单一大版本只做本功能"
- **风险**:4-6 周单一版本承诺,中间遇到阻塞难以拆解
- **建议**:v0.5.0 内部拆 v0.5.0.a（SYS-3 升级）/ v0.5.0.b（FN-BIZ 后端）/ v0.5.0.c（FN-BIZ 前端 + 首页升级）三阶段验收,不打独立 tag 但内部有里程碑

### 4.2 v1.0 新定义（今晚节奏 B 拍板）

- v1.0 = Socket + Oracle Dialect + SYS-3 升级 + FN-BIZ + Docker + 版本显示 + trace_id
- v1.0 前还有 v0.3.0/0.3.2/0.3.7/0.4.0/0.5.0 **五个 minor**
- **风险**:任何一个 minor 延期,v1.0 就延期 · 4-5 月节奏偏乐观
- **建议**:v0.3.2 后打一个"MVP 试点预览 tag"（`v0.3.2` 保持 minor,但产品说明书标注"金融试点可用"),不宣布 v1.0 · 让销售/客户尽早接触

### 4.3 单会话决策链过长（今晚典型案例）

**今晚（2026-07-28）单会话动作序列**：
1. 用户读 lcpt-host 报文 → 问"能做吗" → 我用 Explore agent 摸能力 → 给三方案 A/B/C 成本对比
2. 用户拍板方案 B（先做 pg-testkit + backend Socket 最小闭环）→ 我拉高到方案 C
3. 用户拍板 v0.3.0 单 minor 装完 → 我发现 v0.3.0 有冲突（Oracle+Docker+CR-003）→ 让用户拍 A/B/C
4. 用户拍板方案 A（v0.3.0 让位）+ 补 lcpt-bank → SOCK-5 从"待评估"变身 SOCK-5-A/B/C
5. 我告诉用户 4.5-6 周超单 minor 规模 → 让用户拍 A'/A''/A''' → 用户拍板 A''
6. 用户拍板 A'' 后我问要不要做 GAP 梳理 → 用户拍板做 → agent 报告一份 → verify 打包脚本 0% 是错报
7. 提议三种发布节奏 A/B/C → 用户拍板 B → 4-5 月发 v1.0
8. 我准备开工 v0.3.0 任务计划 → 用户说"先歇一下,复盘"

**统计**：
- **5 次 AskUserQuestion**（多为大范围决策）
- **6 处文档大 Edit**（反馈簿/待办池/路线图/GAP 梳理/复盘触发）
- **1 个新长文档**（能力GAP梳理-2026-07-28.md · 300+ 行）
- **90 分钟内完成**

**风险**：用户被推着走 · 决策稳定性差 · 事后可能反悔（如今晚 SOCK-5 假设 30% 需调整）

**建议改进**：
- **AskUserQuestion 软上限 3 次/会话** · 超过要检查是不是节奏过快
- **大范围决策需 24h 冷静期** · 影响 2+ 版本 或 改 v1.0 定义
- **agent 报告 verify 规则**:agent 报告用于决策文档前,必须 grep/read 至少 1 项关键陈述
